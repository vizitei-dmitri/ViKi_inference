# Онлайн-повторение человека: запуск

Реализованный режим: **две камеры → 21 точка кисти / поза ладони → относительный
retarget → MuJoCo или UR10e**. Данные обрабатываются по мере поступления.
Локоть и плечо не оцениваются; захват и гуманоидная кисть пока не управляются.
Обученная Diffusion Policy для этого режима не нужна.

## Быстрая проверка на имеющейся записи

CPU-образ содержит MediaPipe, Pinocchio, MuJoCo, ur-rtde и SDK геометрии Kinect
/ RealSense. Он собирается отдельно от тяжёлого CUDA-образа offline perception:

```bash
docker compose build live
docker compose run --rm live live \
  --reference data/datasets/40mm-pnp/2026-10-06_11-15-00 --check

docker compose run --rm live live \
  --reference data/datasets/40mm-pnp/2026-10-06_11-15-00 \
  --source recorded --backend mujoco --recorded-speed 0.5 \
  --seconds 12 --auto-bind --gui
```

`--check` проверяет сохранённую калибровку, модели и исходную модельную позу;
соединений с камерами и роботом нет. Последняя команда причинно читает raw RGB-D,
заново оценивает кисть и исполняет новые цели позиционными приводами MuJoCo.
`rec.npz`, `cln.npz` и `plan.h5` для управления не используются. Для headless
проверки убери `--gui`.

В окне MuJoCo Space переключает Bind / Clutch, B — Bind, C — Clutch, Q — Stop.
В терминале работают `b`, `c`, `q` с Enter. Без `--auto-bind` наблюдение начинается
без движения, первая привязка ручная. Автопривязка разрешена только в симуляции
и только один раз. Закрытие окна убирает просмотр; Ctrl+C останавливает сессию.

По умолчанию perception запрашивается на 15 Гц, исполнитель — **50 Гц**.
Визуализация находится в другом процессе и не задаёт частоту исполнителя.
Экспериментальные 125 Гц доступны через `--control-hz 125`, но на текущем хосте
редкие вычислительные выбросы нарушали бюджет 8 мс. Дедлайн останавливает такой
прогон; гарантий hard real-time нет. [Протокол](2026-10-13-live-validation.md).

## Вкладка Live

```bash
docker compose run --rm live-web
```

Открой `http://localhost:8000` → **Live**. Один web-сервис должен владеть портом
8000 и камерами; если обычный `web` уже запущен, сначала `docker compose stop web`.

1. В Reference episode укажи `data/datasets/40mm-pnp/2026-10-06_11-15-00`.
2. Выбери Recorded RGB-D, MuJoCo, All 21 points, Input speed `0.5`.
3. Нажми Start observing. После прогрева должны появиться точки и валидная поза.
4. Нажми Bind & follow, затем проверяй движение. Clutch отпускает привязку;
   Stop завершает сессию. Поле Operator request показывает подтверждение или
   причину отказа исполнителя.

Отдельные 3-D окна показывают кисть в rig-frame и робота в robot-base-frame.
Тройки осей — ориентация ладони и TCP; маркеры — текущая точка и точка привязки.
Переключение вкладок оставляет сессию работающей. Отсутствующие точки остаются
неизвестными, а состарившееся наблюдение отмечается явно.

## Совмещённый просмотр записанного онлайн-прогона

Для совмещённой оценки **уже записанного online-прогона** открой вкладку
**Online review**. Там исходное облако, онлайн-кисть и измеренные суставы
MuJoCo находятся на одной шкале; офлайн-план не используется. Выбери прогон,
нажми ▶, при необходимости Hand detail. Подробности и различие двух часов:
[просмотр inference](2026-10-19-online-review.md).

## Настоящие камеры → MuJoCo

Reference episode задаёт требуемые устройства, factory calibration, режимы
изображений и измеренные extrinsics. Камеры должны физически стоять в том же rig;
перестановка требует новой калибровки и нового reference. Автоматическая проверка
ловит подмену устройств / factory calibration / размеров, но не физическое
перемещение камеры с тем же серийным номером.

В web сначала запусти камеры штатным Cameras → Start all с режимами reference,
затем выбери Live cameras / MuJoCo. CLI сам владеет камерным менеджером:

```bash
docker compose run --rm live live \
  --reference data/datasets/40mm-pnp/2026-10-06_11-15-00 \
  --source cameras --backend mujoco --seconds 120 --gui
```

Для этого эпизода исходные Kinect режимы — RGB 1920×1080, depth 640×576
NFOV_UNBINNED, requested 30 fps. Нужны обе Kinect, штатные независимые xHCI и
sync-кабель из [SETUP_GUIDE](../SETUP_GUIDE.md). Hardware sync проверяется после
прогрева буферов. В сцене должен быть один человек с выбранной кистью: текущая
MediaPipe конфигурация не решает многопользовательскую ассоциацию.

Bind запоминает текущую точку кисти и текущую модельную FK робота; далее
смещение переносится с масштабом `0.25`. Начальная привязка не тянет робота к
абсолютной координате кисти. Follow palm orientation / `--orientation` включает
перенос вращения ладони; при пропаже её опорных точек привязка отпускается.

## Ethernet и UR10e

IP робота: **192.168.0.100**. Подключи Ethernet от компьютера к роботу. На
компьютере для этого проводного соединения выставь IPv4 Manual:
`192.168.0.10`, маска `255.255.255.0`, gateway / DNS пустые. В NetworkManager
отметь использование только для ресурсов этого соединения, чтобы оно не меняло
маршрут интернета. На пульте проверь IP `192.168.0.100` с той же маской.

```bash
ip route get 192.168.0.100
ping -c 3 192.168.0.100
docker compose run --rm ur ur-status --host 192.168.0.100
```

Маршрут должен идти через Ethernet, а не VPN. `ur-status` получает идентичность
и состояние без загрузки управляющего скрипта. На пульте робот должен быть
готов к работе в Remote Control; нужные настройки и первый offline replay
описаны в [UR10e execution](ur10e_execution.md).

Перед live UR требуется файл регистрации **rig → robot base** и плоскости пола
в robot-frame. [Пример](live_mapping.example.json) содержит неподтверждённые
заглушки. Скопируй его в `data/live_mapping.json`, внеси измеренные значения:

- `rotation_robot_rig` — proper 3×3 rotation: `v_robot = R @ v_rig`;
- `floor_normal_robot`, `floor_offset_m` задают свободное полупространство
  `normal · p_robot >= offset`, значения в метрах;
- `source_calibration_id` обязательно возьми из `--check` для привязки файла к reference;
- `confirmed: true` ставится после проверки регистрации, не для обхода проверки.

Относительный режим не требует translation для начальной цели, но правильные
направления осей и положение пола всё равно нужны. Номинальная модель arm-only
не учитывает установленный инструмент, стойку, стол и предметы. Их физические
зазоры проверяются на стенде отдельно.

```bash
docker compose run --rm live live \
  --reference data/datasets/40mm-pnp/2026-10-06_11-15-00 \
  --source cameras --backend ur10e --host 192.168.0.100 \
  --mapping-json data/live_mapping.json --execute --seconds 30
```

Сначала начинается наблюдение и receive-only доступ к UR. Для первого теста
держи кисть неподвижной, робот должен стоять в проверенной свободной позе.
Нажми `b` только после валидного наблюдения, затем сделай небольшое движение.
Управляющий скрипт RTDE загружается при Bind; автоматического homing нет.
`c` отпускает следование, `q` / Ctrl+C завершают сессию. В web тот же порядок:
Physical UR10e, IP, Mapping JSON, Enable physical motion, Start observing, Bind.

Потеря наблюдения или отказ IK вызывают торможение и сброс привязки. Возврат
кисти сам движение не восстанавливает — нужен новый Bind. Ошибка tracking,
дедлайна, состояния контроллера или журнала завершает исполнение. Replay и live
используют общий lock владения роботом. Реальная аппаратная проверка этого
live-кода пока не выполнена.

## Журналы и тесты

Каждый запуск пишет уникальную папку `data/live_sessions/<id>/`: `manifest.json`,
`hand.jsonl`, `session.json`, подкаталог `executor/` с `execution.h5` и отчётом.
Там сохраняются original source timestamps, validity, калибровка / model hashes,
цели человека, отправленные команды, measured joints и причины остановки.
Запись не превращается автоматически в подтверждённый dataset для RL.

```bash
docker compose build live-test
docker compose run --rm live-test
```

Дальнейшая Diffusion Policy должна подавать ограниченные свежие действия через
отдельный policy adapter; текущий `HumanTarget` предназначен для позы человека.
21 точка кисти уже сохраняется для последующего hand-retarget, но physical
feedback и управление гуманоидной рукой потребуют отдельного драйвера.
